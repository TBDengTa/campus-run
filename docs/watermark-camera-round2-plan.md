# 水印相机第二轮修订（合成成片体积预算 + 横屏 UI 重设计）

> **状态：已实施（2026-11-13）。** 口径定稿 + 代码落地均完成；真机验收（横竖屏各拍一组、
> 弱网上传）为人工事项。本文件是第二轮的**口径唯一说明**；第一轮口径仍以
> `docs/watermark-camera-plan.md` 为准（§11 已含 R1 乐观预览 / R2 横屏旋转 / R3 成片规格 / R4 横屏 UI）。

## 0. 一句话目标

① 把水印相机的**合成成片体积压进上传通道的安全区**（根治「拍照后上传失败」）；
② 横屏下的 UI 从「竖屏布局硬转」重设计为**横屏专属布局**（全屏取景 + 双手拇指可达）。

## A. 上传失败：根因与修复

### A1. 各层事实（排查结论，别猜）

| 层 | 现状 | 结论 |
|---|---|---|
| 合成产物 | `canvasToTempFilePath` **quality 1.0 + 满分辨率**（第一轮为守「不限画质」） | ⚠️ **体积放大器**：相机硬件编码器 12MP 出 3~6MB，canvas q1.0 同尺寸重编码可到 **10~20MB**（JPEG 软编码在高 quality 段效率远差于硬件编码器），成片可达原片 3~4 倍 |
| `wx.uploadFile` | `utils/request.js::uploadCheckPhoto` **未设 timeout（默认 60s）**；真机对超大请求体不稳（10MB 级经常直接 fail） | ⚠️ 第二瓶颈：大文件 × 校园弱上行 = 超时 / 通道拒绝 |
| 失败兜底 | `retryWithCompressed`（q80 / 长边 2560 重传一次）只对 **size ≥ 2MB** 触发 | 兜底本应救回，但压缩重试本身也可能失败（`wx.compressImage` 对超大 canvas 产物在部分机型失败），或重传仍超时 → 用户看到「失败」 |
| nginx | `client_max_body_size 0`、`proxy_send/read_timeout 600s` | ✅ 无上限（用户 2026-11-12 口径未破坏） |
| 服务端 | multer **不设 fileSize**；`verify-check-photo-unlimited.js` 已验证 20MB 可过 | ✅ 无上限，**本轮零改动** |
| EO | 回源超时远大于 60s，不是先撞的那一层 | ✅ 排除 |

**根因链**：canvas q1.0 满分辨率 → 成片 10~20MB → 撞真机 uploadFile 通道实际上限 / 60s 默认超时 →
失败；压缩重试兜底在部分机型同样失败。**从源头定成片规格，比修重试更根本。**

### A2. 修复口径（已定稿）

**成片规格预算**（常量单点在 `utils/watermark.js`，与 buildLines/computeLayout 同处）：

| 常量 | 值 | 说明 |
|---|---|---|
| `OUT_LONG_EDGE` | **2560** | 输出长边。留证复核在屏幕上看，2560 足够；同时把画布位图内存压到 ~2560×1920×4B ≈ 19MB，低端机也稳 |
| `OUT_QUALITY` | **0.92** | 视觉近无损（水印相机的通用档），12MP 源缩到 2560 后典型成片 **1.5~3MB** |
| `OUT_MAX_BYTES` | **8MB** | 预算红线：超出自动降一档重出（2048 / 0.85），仍超再降（0.75）。**闭环只看文件实际大小**，不赌估算 |

合成流程改为：解码原图（护内存先降到 4096 内）→ 按 `OUT_LONG_EDGE` 缩放绘制 → `q0.92` 输出 →
`getFileSystemManager().getFileInfo` 查实际体积 → 超预算降档重出（复用已解码图，只重画重出，秒级）。
乐观预览流程不变（A 轮 R1）；降档重出期间预览显示「正在合成水印…」，与现状一致。

**上传通道加固**：`uploadCheckPhoto` 的 `wx.uploadFile` 显式 `timeout: 120000`
（默认 60s 对弱网 2~4MB 上行偏紧；120s 给足余量，失败文案继续透传真实原因）。
`retryWithCompressed` 兜底**原样保留**（对相册超大原图仍必要）。

### A3. 为什么这不违反「解除所有上传照片限制」红线（2026-11-12）

| 红线保护的 | 本轮是否触碰 |
|---|---|
| 用户**原图**（相册路径）：`chooseMedia` original **原样直传**，不做上传前压缩 | ❌ 一行不动 |
| 服务端不设体积/张数上限、nginx `client_max_body_size 0` | ❌ 零改动 |
| `tools/verify-check-photo-unlimited.js` | 原样必须通过 |
| 水印相机**合成成片**的规格 | ✅ 本轮定义 —— 合成本来就是客户端再编码（第一轮方案 §7.6 已声明「重编码一次不可避免」），成片规格是产品定义的一部分（对标主流水印相机 App 的输出规格），不是「为了过上传限制而压缩用户的图」。规格写进代码注释与检查器，防止日后被误读成「压缩回潮」 |

一句话：**红线管的是「别挡用户的原图」，不管「水印成片长什么样」。**

### A4. 验证

- 真机复测前先读失败 toast 文案（`uploadCheckPhoto` 已透传真实原因：超时 / 413 / HTTP 无响应）——修复前后各留一份，定位是哪一层；
- 修复后预期：水印拍照 → 合成（1.5~3MB）→ 上传成功；相册原图路径行为与第一轮完全一致；
- 回归：`check-watermark-camera.js` 断言从「quality 1 / 原尺寸」改为「规格常量 + 体积闭环 + uploadFile 显式 timeout」；`check-page-runtime.js` 补「超预算自动降档」用例；`verify-check-photo-unlimited.js` 原样通过。

### A5. 第三轮真机修订（2026-11-13「水印拍出的照片又出现了无法上传」）

第二轮把 quality 从 1.0 降到 0.92、长边钉到 2560，但**成片还是传不上去**。
漏掉的是**导出像素数**：

```
wx.canvasToTempFilePath 的 destWidth 默认值 = width × screen.pixelRatio
```

本页画布 `canvas.width = 2560`（后备缓冲区像素），不传 destWidth 时微信按默认值再乘一次 DPR：
DPR=3 的机子实际输出 **7680×5760（44MP）**，q0.92 成片几十 MB → 上传通道直接失败。

**为什么「体积闭环」没救回来**（这是最阴的一环，两个 bug 咬在一起）：

1. 每一档都按同样的 DPR 放大 → **三档全部超 8MB 预算**；
2. 循环最后一档是「无条件接受」（`i === OUT_ATTEMPTS.length - 1`）→
   于是闭环**看起来在正常降档**（日志/用例都能验），交出去的仍是几十 MB。

顺带还有一处 fail-open：旧判定 `if (!size || size <= OUT_MAX_BYTES || last)` ——
`getFileInfo` 一旦失败（size=0）就当通过、第一档直接放行。

### A5.1 修法（三条，都在 `wcamera.js` 合成侧）

| # | 改动 | 说明 |
|---|---|---|
| 1 | `destWidth/destHeight` 显式取 `canvas.width/height`（1:1） | 规格从此真的成立：2560 就是 2560，典型成片回到 1.5~3MB |
| 2 | 判定改 `(size > 0 && size <= OUT_MAX_BYTES) \|\| isLast` | 体积读不到**不再算通过**，继续降档 |
| 3 | 新增 `lastProduced`：降档途中某档抛错但前面已出图 → 用那张 | 别把已经花 2 秒合成好的带水印图扔掉退回无水印原图 |

⚠️ **反向约束：不要传 `x/y/width/height` 区域参数。** 区域默认就是「整块画布」
（`packageAdmin/class-status` 的分享图同样不传区域、导出完整画布，现网已验证）；
而部分机型把这几个参数按 canvas 的 **CSS 尺寸**解释 —— 本页离屏画布 CSS 只有 320×240，
传了可能只导出左上角一小块，现象还会被误读成「画质变差」。只钉 dest 像素数是最小安全改动。

### A5.2 现场自证（下次再报「传不上去」不用再猜）

`entry.js::uploadOne` 的失败文案现在带**这张图的真实体积**：
「上传超时…（照片 28.41 MB）」= 合成侧规格没生效；「（照片 2.13 MB）」= 网络/服务端问题。
两种根因修法完全相反 —— 这正是本轮排查最花时间的地方。服务端文案已含 MB/KB 时不重复追加。

### A5.3 回归

- `check-watermark-camera.js`：`destWidth/destHeight` 存在且取自 `canvas.width/height`（不许写死数字）、
  反向断言**不许**出现区域参数、闭环不再 fail-open、`lastProduced` 兜底存在、
  合成产物 `saveFile` 落盘到用户目录、落盘失败回退临时路径、过期文件清理、成片体积在确认界面可见；
- `check-page-runtime.js` 新增用例：导出参数 1:1 断言、`getFileInfo` 失败时逐档降到底、
  降档途中失败仍保留已产出的带水印成片、落盘成功/失败两条路径、失败文案带体积（且已含体积时不重复追加）。

### A6. 第四轮真机修订（2026-11-13「拍照上传就失败」而**相册照片一直正常**）

用户反馈：相册选图能传，水印相机拍的就失败。这条对照**直接排除了体积**——
相册原图普遍 6~12MB，比水印成片（1.5~3MB）大得多，能传就说明上传通道/服务端/权限都没问题。

真正的差别是**文件从哪来、活多久**：

| | 相册 | 水印相机（旧） |
|---|---|---|
| 来源 | `chooseMedia` 原始临时文件 | `canvasToTempFilePath` 合成产物 |
| 生成到上传之间 | 同一个页面里，立刻上传 | **相机页 `navigateBack` 销毁后**才在 entry 上传 |
| 连拍时临时文件量 | 1~2 张 | 每张「12MP 原图 3~6MB + 合成图」两份 |

微信对临时文件的态度是明确的：**随时可能被系统清理**。连拍几张后临时区触顶，
最早那批合成图会被回收 —— 等 entry 去上传时文件已经不存在，上传通道直接 fail
（在真机上就表现为「拍照就失败」，而单张相册照片永远碰不到这个窗口）。

**修法：合成完成后立刻落盘到用户目录**（`FileSystemManager.saveFile`，
`wx.env.USER_DATA_PATH`，200MB 配额、不随页面销毁/临时区回收消失），托盘与上传都用这个稳定路径；
落盘失败退回临时路径（回到旧行为，不丢照片）。连拍会攒文件，所以相机页 `onLoad` 清理 **24h 前**的
`wm-*` 文件（正在用/待重传的在时间窗内，不会被误删）。

顺带把「是不是体积问题」变成**界面可回答**：确认界面显示 `将上传 · 2.14 MB`，
失败文案也带这张图的真实体积 —— `>8MB` 基本是合成侧规格失效，`<4MB` 则一定是网络/服务端，
两种根因修法完全相反。

回归：`check-watermark-camera.js` 5 条（落盘/回退/用落盘路径/过期清理/体积可见）+
`check-page-runtime.js` 落盘成功与失败两条路径。

### A7. 第五轮（2026-11-13「超过 250KB 就传不上去，开调试连报错都没有」）

先给结论：**代码里不存在任何 250KB 门槛**（已核对：`routes/upload.js` 的 multer 不设 `fileSize`、
nginx `client_max_body_size 0`、前端 `uploadCheckPhoto` 无体积判断、`express.json` 只作用于 JSON
不作用于 multipart）。而且**相册原图（6~12MB）能传**——体积假说不成立（同体积的相册图应该一起挂）。

真正能造成「**连报错都没有**」的只有两种形态，本轮把它们全堵掉：

| 形态 | 为什么会静默 | 修法 |
|---|---|---|
| `getFileInfo` 既不 success 也不 fail（个别机型） | `appendWatermarkPhotos` 的 `Promise.all` 永不落地 → 照片不入列、无任何提示 | `resolvePhotoSource` 每份 1.5s 超时；两份都失效 → `console.error` + toast「有 N 张照片文件已失效」 |
| `wx.uploadFile` 既不 success 也不 fail | `uploading` 恒 true → 之后每张在 `uploadPending` 入口 `return`，照片不出现、控制台无报错 | 单张上传套 **150s 硬超时**；`uploading` 复位放 `finally` |

同时把「只信一条路径」也改掉了：

- 落盘改用 **`copyFile` 而不是 `saveFile`**（saveFile 是移动，临时路径随即失效，副本读不到就没退路）；
  相机页把 `{ path: 主副本, backupPath: 临时副本 }` 一起回传，**上传前逐一验证哪份真能读**；
- 失败兜底压缩不再「<2MB 直接跳过」（旧逻辑让一张 600KB 的成片失败后毫无补救）：
  改成 **2560 → 1600 两级**逐级缩小重传；
- 失败必打 `console.error('[entry] 检查照片上传失败', { path, size, code, message, raw })` ——
  真机/开发者工具可直接捞原始 `errMsg`，不再靠猜。

⚠️ 若本机复测仍失败，先做一个**决定性的对照**：用「相册」选一张 >250KB 的图上传。
- 相册也失败 → 不是水印相机代码的问题，是**网关/服务端**（看 console 里的 `raw`：413 / timeout / 无响应）；
- 相册正常、仅水印失败 → 看 console 的 `size` 与 `path`，能直接区分「文件失效」与「通道拒绝」。

## B. 横屏 UI 重设计

### B1. 现状问题（第一轮只开了旋转，没做布局）

竖屏三段式（导航条 / 取景区 / 底部控制条）转横屏后：

1. **取景区被压扁**：`100vh` 列布局下，导航 + 托盘 + 快门条占掉近 40% 高度，取景画面只剩一条；
2. **快门条横贯全宽**：横屏双手持机时，左端「完成」右手拇指够不着，右端空置浪费；
3. **自定义导航整条黑带**占顶部一行——横屏纵向空间最稀缺，这条带子零收益；
4. 刘海屏横屏时缺口在侧，现有 `safe-area-inset-bottom` 不覆盖左右安全区。

### B2. 设计原则

- **全屏取景**：横屏下相机画面铺满整屏，一切控件浮在其上（主流相机 App 的横屏形态）；
- **拇指可达**：横屏双手持机 → 左下角归左手（托盘/重拍），右下角归右手（快门/用照片）；
- **竖屏不动**：竖屏布局已过第一轮验收，本轮只加横屏分支，不回改竖屏；
- **旋转无跳变**：布局切换用 `@media (orientation: landscape)` + `isLandscape` 双轨（纯样式走媒体查询，结构分支走 JS 标记），转屏瞬间不闪白。

### B3. 横屏布局（三态，快门右下已定稿）

**取景态**：

```
┌────────────────────────────────────────────────┐
│ (←)                                            │ ← 返回：左上浮层圆钮（导航条隐藏）
│                                                │
│                 相机画面（全屏）                 │
│                                                │
│ ▓▓▓▓▓▓▓▓ 水印浮层（左下）▓▓▓▓▓▓                │
│ 晚自习检查 · 1号教学楼201                        │
│ 2026-11-13 周五 21:04:36                       │
│ 生活部 · 张三                                   │
│                                                │
│ ┌──┐┌──┐┌──┐                    ╭─────────╮   │
│ │01││02││03│ ←托盘（左下横排）    │ 完成(3)  │   │ ← 右列：完成在快门上方
│ └──┘└──┘└──┘                    │    ◉    │   │ ← 快门右下（右手拇指）
│                                  ╰─────────╯   │
└────────────────────────────────────────────────┘
   右缘留 safe-area-inset-right（横屏刘海侧）
```

**预览态**：黑底全屏，合成图 `aspectFit` 居中；左下「重拍」（左手）、右下「用照片 / 合成中…」（右手，即快门位换图标）；顶部提示条（正在合成水印 / 这张照片将带以上水印）不变。

**引导面板**（相机不可用）：居中卡片，横竖屏同构，仅宽度上限收窄。

### B4. 实现要点

| 项 | 做法 |
|---|---|
| 方向标记 | `onLoad` 里 `wx.onWindowResize` 比较 `size.windowWidth > windowHeight` 置 `data.isLandscape`，`onUnload` off；首帧用 `wx.getWindowInfo()` 初始化（进页就横着的场景） |
| 纯样式切换 | WXSS `@media (orientation: landscape)` 覆写：导航条隐藏（改浮层返回钮显示）、控制条改绝对定位右列、托盘改左下横排、预览按钮改左右下角 |
| 结构分支 | 仅快门簇与托盘的**容器位置**用 `wx:if="{{isLandscape}}"` 分支（WXML 两套位置、同一批节点语义）；文案/事件零分叉 |
| 安全区 | 横屏用 `env(safe-area-inset-left/right)` + `wx.getWindowInfo().safeArea` 兜底，快门右列、返回左上都让出缺口 |
| 焦点不丢 | 转屏时 `camera` 组件会重建（组件级行为），`binderror` 已有兜底；托盘与在途合成（seq）都是 data 态，转屏不丢 |
| 视觉令牌 | 全部 `--tt-*`（品牌快门、软底浮层），暗色基底维持 `#0a0a0a`，不引入新色 |

### B5. 回归

- `check-page-runtime.js`：横屏标记初始化 + 转屏回调改 `isLandscape` 不抛、托盘/在途合成状态不丢（桩 `onWindowResize` 触发）；
- `check-watermark-camera.js`：断言横屏媒体查询块存在（控制条右列 / 托盘左下）、`isLandscape` 接线、safe-area 引用；
- 真机验收：横竖各拍一组（转屏连续切换 3 次不闪白、托盘不丢）、横拍水印方向正确、刘海机右侧不裁快门。

### B6. 第三轮真机修订（2026-11-13 截图「横屏占比太大、还挡画面」，已落地）

用户截图：横屏里「卫生检查 · 1号楼(女生宿舍) 201 / 2026-11-13 周五 / 13:35:10 / 主席团」
四行大字占了左半屏，右侧一个巨大白圆（快门）+ 巨大「完成」胶囊 —— 画面基本被 UI 吃掉。

六个成因（**全是静默的**：不报错、不白屏、颜色都在，所以第一轮验收没发现）：

| # | 成因 | 修法 |
|---|---|---|
| 1 | **横屏块里全是 rpx**。rpx 恒等于 `windowWidth/750`，横屏时 windowWidth 是屏幕**长边**：812×375 的机子 1rpx≈1.08px，而竖屏（375 宽）才 0.5px —— **同一份 rpx 数值横屏膨胀 ≈2.16 倍**。竖屏 42rpx 时间大字（≈21px）横屏变 ≈45px、128rpx 快门（≈64px）变 ≈138px（占屏高 37%） | 横屏媒体查询块内**一律 px、零 rpx**（检查器反向断言）。预算：时间大字 16px、快门 56px、托盘 44px、胶囊 28px |
| 2 | **WXML 写的 `wm-land-pill / wm-land-finish / wm-land-primary` 在 WXSS 里根本没有定义**（上一版只改了 WXML 类名，样式还挂在没被使用的 `wm-land-btn` 上）→ 控件按「无样式」裸排，尺寸全靠默认值 | 结构类与样式一一对应（检查器逐类校验「WXML 用到的 `wm-land-*` 在 WXSS 有定义」），不留死类名 |
| 3 | **两套取景口径打架**：`computeLandLayout` 的「4:3 居中卡片」用内联 style 覆盖，而 WXSS 横屏块又要求 `.wm-viewfinder` 全屏 absolute —— 内联只给宽高不给位置，卡片被全屏规则拽到左上，控件条与画面互相压 | **取消 JS 实算卡片**（`landCardW/H`、`computeLandLayout` 全删），取景单一口径 = 全屏，控件全部浮在四角 |
| 4 | **暗色取景底套了亮色文字令牌**：`--tt-text-2/3`、`--tt-line` 是亮色主题的深灰，压在 `#0a0a0a` 上等于隐形（「完成」「重拍」「相机不可用」看不清） | 本页固定暗色：文字/描边走白色系（品牌橙仍 `--tt-brand`），检查器反向断言不再出现 `var(--tt-text-*/line)` |
| 5 | **成片水印同样只按图宽等比**：`computeLayout(outW)` 横拍 4032×3024 → 时间大字 269px、底条 1258px（占画面 42%）。UI 改小只解决「取景时挡」，照片里那半黑条还在 | `computeLayout(outW, outH)`：横屏基准换成**图高**并收紧一档（`LAYOUT_LAND`），底条 ≈25%；竖屏逐字不变（有回归护栏） |
| 6 | **横屏 `.wm-controls` 是覆盖全屏的透明壳**，没关 pointer-events → 吃掉整屏点击，相机「点屏幕对焦」静默失效 | 壳 `pointer-events:none`，托盘 / 右列 / 重拍各自 `auto` |

版式落点（横屏）：水印浮层从「整幅宽渐变压带」收成**左下角小卡**（`right:auto` + `max-width:52%`，
bottom 让开托盘）；合成提示从「顶部整幅黑带」改成**顶部居中胶囊**；托盘 40% 宽上限、
预览态抬高 52px 给左下「重拍」；引导面板横屏改横排两钮、宽度收窄；
`.wm-controls` 透明壳 `pointer-events:none`（真控件各自 auto）—— 否则整屏点击被吃掉、相机点屏对焦失效。

**成片那一半（同一根因，别只改 UI）**：`utils/watermark.js::computeLayout(outW, outH)`
横屏（W>H）的等比基准从**图宽换成图高**并整体收紧一档（`LAYOUT_LAND`：f2 = H/24），
行1 折行宽度限到 62% 画面宽。旧口径下 4032×3024 横拍 = 时间大字 269px、底条 1258px
（占画面 42%）—— 复审台里半张照片是黑条。现在横屏底条 ≈25% 画面高，竖屏**逐字不变**
（检查器「竖屏规格零变化 f1=126/f2=202/f3=108/maxW=2722」钉住，防顺手把竖屏也改小）。

回归：`tools/check-watermark-camera.js` 新增 11 条断言 ——
横屏块零 rpx / 快门 ≤64px / 浮层收进左下（max-width + right:auto）/ 时间大字 ≤20px /
`wm-land-*` 类都有定义 / 不再有 JS 实算卡片 / 暗色底不套亮色文字令牌 /
透明控制层不吃触摸 / 横屏成片底条 ≤30% 画面高 / 横屏时间大字 ≤8% 画面高 / 竖屏规格零变化。
`tools/check-page-runtime.js` 的「水印相机」target 同步补 computeLayout 横竖屏比例用例。
